# Ускорение личного кабинета AniDachi

Дата исследования и реализации: 1 октября 2026. Статус: реализация и локальная
проверка завершены; доставка, измерения и ручная приемка на staging еще не проведены.

База: `5dc2a4a7` (UI-релиз PR #386 на staging). Ветка реализации:
`codex/account-loading-performance`. Next.js 15.5.23. Описанные ниже исходные
наблюдения относятся к базе до этой оптимизации, а не к текущему коду.

## Прогресс реализации

- [x] Друзья и группы отображаются независимо; медленные/недоступные группы не скрывают друзей.
- [x] Общие layout и страницы используют один React.cache-загрузчик identity в рамках серверного рендера. API-проверки доступа не кешируются.
- [x] При открытии отдельного документа friends/billing получают серверный снимок. Billing сохраняет проверку живой website refresh-family и владельца из существующего API.
- [x] При явном клике в меню кабинета friends/groups/billing GET начинается параллельно RSC-переходу. Клиент использует этот запрос один раз, без дубля после mount. Запрос привязан к владельцу, имеет таймаут 15 секунд и удаляется после использования; неиспользованный отменяется при следующем переходе, logout или TTL. Событие изменения социальных данных отменяет еще не использованные запросы друзей/групп, даже до монтирования страницы. Наведение курсора не запускает его.
- [x] RSC-переходы не делают второй серверный bootstrap. Для прямого SSR срок снимка консервативно учитывает возраст документа, а не часы пользователя. Старый документ/back-navigation требует свежего чтения; срок trial не начинается заново.
- [x] Обычный focus подписки использует GET и сохраняет еще действующее отображение. Stripe return и явный refresh по-прежнему сверяют Stripe.
- [x] Конкурентные 401 используют общий выполняющийся refresh; отложенный 401 учитывает уже прошедший refresh. Отмененный запрос не повторяется.
- [x] Входящие не ждут отправленных и отметки прочтения. Раздельные поколения не позволяют входящему действию блокировать отправленные; устаревшая отметка прочтения не восстанавливает строки после мутации.
- [x] Начальные preferences/history читаются параллельно между независимыми access-проверками.
- [x] Изменение текущего эпизода запускает один editor GET; при закрытии/замене запроса чтение отменяется. Название/обложка уже показывались сразу и сохранены.
- [x] Добавлено состояние загрузки разделов, без тяжелого автоматического prefetch.
- [x] Полный web suite, typecheck, production build и независимое ревью окончательного diff завершены; замечания ревью исправлены и проверены регрессиями.
- [ ] Доставить на staging, сравнить одну последовательность переходов до/после и получить ручную приемку владельца.

Решения по границам: общий кеш личных данных между маршрутами, кеш editor-ответов,
кеш Stripe-цен, изменения SQL/индексов и регионов не добавлены. Для них нет
достаточных измерений; кеш редактора потребовал бы отдельной инвалидации
owner/generation/accessEpoch и всех мутаций. Реальные чтения сохраняются, поэтому
эта работа не обещает мгновенные данные при любой сети или офлайн.

## Исходное состояние до оптимизации

### Друзья и группы

- `app/account/friends/page.tsx` передает клиенту только данные текущего пользователя. Друзья и группы запрашиваются после монтирования клиентского компонента.
- `FriendsWorkspace.refresh` выполняет запросы параллельно, но устанавливает оба результата только после `Promise.all`. Медленные группы задерживают показ друзей; ошибка групп блокирует применение успешно полученных друзей.
- Начальное состояние списков пустое при каждом новом монтировании. Provider кабинета сейчас сохраняет только состояние интерфейса, а не данные.
- `listFriends` сначала вызывает `ensureProfileForUser`, затем читает связи, затем пакетно получает профили и пользователей друзей. Запроса на каждого друга отдельно в этом пути нет.
- `listFriendGroups` сначала вызывает `archiveGroupsOverLimit`, затем читает группы, участников и профили. Проверка лимита сама читает пользователя и активные группы и при необходимости архивирует лишние группы. Это побочный эффект чтения: нельзя бездумно запускать его при предварительной загрузке ссылки или просто удалить ради скорости.
- Layout, страница и API повторно вызывают чтение пользователя/профиля. Реальное число сетевых обращений внутри одного серверного рендера нужно измерить: Next.js может автоматически объединять часть одинаковых GET. Повторные отдельные API-запросы от этого не исчезают.

### Подписка

- Серверная страница не передает начальные данные подписки: клиент начинает с `overview = null` и делает следующий запрос после загрузки страницы.
- `BillingClient.load` вызывает `setOverview(null)` перед любым обновлением.
- Каждый возврат фокуса вызывает `load(true)` — POST со сверкой Stripe.
- На чтении обзора запрашиваются цены Stripe, включая записи старых подписок. Возможность кешировать проверенные публичные цены надо отделить от состояния подписки и прав пользователя.
- Уже существует ограниченный срок действительности отображения: до 60 секунд, сокращаемый ближайшим окончанием trial, тарифа и другими границами. Его нельзя продлевать повторным использованием сохраненного результата.

### Библиотека и тайтлы

- Начальные данные библиотеки уже загружаются на сервере. Перенос на сервер сам по себе здесь ничего не исправит.
- `loadWatchLibraryData` последовательно читает доступ, настройки, историю и снова доступ. Внутренние функции дополнительно защищены проверками до и после чтения.
- Настройки повторно читаются внутри `loadHistory`; `getPreferences` делает upsert с ignoreDuplicates и затем select. Возможность сократить эти обращения требует сохранения создания настроек нового аккаунта и проверки поколения истории.
- Тайтл отдельно читает editor API при открытии. Повторное открытие не использует предыдущий результат.
- Общий `client-api.ts` после 401 отдельно обновляет сессию и повторяет запрос. Одновременные запросы не объединяют refresh. Это подтвержденная особенность кода, но массовый refresh в браузере пока не воспроизведен.

### Другие вкладки

- Профиль, формы обратной связи и запросов функций также используют повторяющиеся загрузчики пользователя/профиля.
- Analytics вызывает `/api/me` на изменение pathname. Это дополнительная нагрузка, но не подтвержденная блокировка основного экрана. Analytics специально не обновляет сессию — это ограничение сохранить.
- Уведомления ждут и входящие, и отправленные приглашения, затем подтверждение прочтения перед показом входящих. Колокольчик имеет собственный запрос счетчиков. Данные входящих и счетчик можно согласовать, не задерживая список подтверждением прочтения; отмечать прочитанным только реально открытый пользователем экран, не prefetch.
- Среди вкладок кабинета отдельный `loading.tsx` сейчас есть только у библиотеки. Остальные переходы могут выглядеть как зависший старый экран.

## Предлагаемое устройство

1. Начинать независимые чтения раньше. Для друзей и подписки передавать начальные данные из серверного слоя напрямую, без вызова собственного HTTP API из Server Component. Долгие части изолировать через Suspense, чтобы не заблокировать весь кабинет новым общим await.
2. Разделить готовность ресурсов. Друзья показываются после получения друзей; группы и их ошибки не должны скрывать список. Аналогично входящие уведомления не ждут отправленных и подтверждения прочтения.
3. Различать первоначальную загрузку и обновление. На обновлении сохранять только еще допустимые данные текущей сессии. При ошибке обновления не подменять существующий список ложным пустым состоянием.
4. Убирать повторную работу в рамках одного серверного рендера через узкий read-only загрузчик и React.cache. Не оборачивать глобально все функции db/auth: повторные проверки полномочий до/после операции обязаны оставаться независимыми.
5. Повторное использование данных между вкладками — только в памяти, с ограниченным сроком, владельцем и поколением сессии. После выхода, повторного входа, смены аккаунта или потери доступа очищать соответствующие данные и игнорировать запоздавшие ответы. Не использовать общий HTTP/CDN-кеш для личного кабинета.
6. Для подписки тихая проверка текущего состояния и сверка Stripe — разные операции. Сверка обязательна после возврата из Stripe и явного действия; обычный focus не должен безусловно очищать экран и запускать ее заново. На реальном истечении срока действительности состояние должно быть перепроверено; платные действия всегда проверяет сервер.
7. Публичные данные цены можно рассмотреть для отдельного ограниченного кеша с ключом окружения/аккаунта Stripe и price ID. Подписки, trial, права, суммы конкретной операции и подтверждения платежа в такой кеш не входят.
8. Общий refresh сессии: один выполняющийся refresh для конкурентных 401 в текущем контексте входа, после чего каждый актуальный запрос повторяется максимум один раз. Сохранить отмену запросов, отказ при неуспешном refresh, поведение вращения cookie и проверки владельца. Отдельно проверить вход/выход в другой вкладке; схема одной Promise в одном окне не решает межвкладочные гонки автоматически.
9. Для истории сначала измерить вложенные RPC. Параллелить только независимые чтения внутри существующих границ доступа. Любое объединение запросов в SQL/RPC — отдельная задача после доказательства необходимости. Не кешировать проверки before/after так, чтобы обе вернули один старый результат.
10. Для тайтла сначала показывать уже известные название/обложку, а детали загружать отдельно. Ограниченное повторное использование editor-данных возможно только с ключом owner, generation, accessEpoch, provider и titleKey и сбросом после изменения/удаления. Не перезаписывать несохраненное редактирование фоновым ответом.
11. Добавить мгновенный отклик навигации и легкие состояния загрузки. Предварительную загрузку включать адресно, с учетом побочных эффектов чтения и стоимости запросов, а не разом для всех тяжелых вкладок.

SWR поддерживает многие механизмы обновления и объединения запросов, но сам по себе не решает наши проверки владельца, срока действия и поколения истории. В проекте его сейчас нет. На первом этапе достаточно устранить конкретные задержки в существующем коде; отдельный слой общего клиентского кеша стоит вводить только с явными правилами очистки и после проверки фактической необходимости.

## Порядок работы

1. Зафиксировать повторяемый baseline на staging: первый вход, переходы, повторные открытия, возврат фокуса, истекшая сессия. Собирать длительности фаз и количество обращений, без токенов, cookie и личных данных.
2. Общие загрузчики аккаунта и начальная загрузка друзей; независимое отображение друзей/групп. Проверить создание и редактирование групп, лимиты, запросы дружбы и удаление.
3. Начальные данные подписки и обновление без мигания в пределах срока действительности. Проверить trial, смену периода/тарифа, отмену/возврат продления, возвращение из Stripe, истечение доступа и ошибки.
4. Координация refresh сессии и уведомлений. Проверить конкурентные запросы, отказы, отмену, выход/вход и межвкладочные события.
5. Библиотека и тайтлы по отдельным измерениям. Сохранить защиту от смены аккаунта, тарифа и поколения истории, удаления и запоздавших ответов.
6. Сравнить одну и ту же последовательность действий до и после на staging. Отдельно оценить холодное открытие и повторный переход, типичную и плохую сеть, небольшие и большие списки. Для p50/p95 собрать серию измерений, не делать вывод по одному быстрому запросу.

## Критерии приемки

- Клик по вкладке получает немедленный понятный отклик; готовые части не ждут посторонние ресурсы.
- Внутри действующей сессии обычное обновление не заменяет корректную подписку или списки пустым экраном.
- Успешная операция обновляет связанные экраны; старый запрос не возвращает удаленного друга, группу или историю.
- Выход, смена пользователя, истечение срока или потеря доступа немедленно прекращают использование недопустимых данных.
- Начальные серверные данные не вызывают автоматический дублирующий запрос сразу после монтирования без необходимости.
- Предварительная загрузка не подтверждает прочтение уведомлений и не запускает бизнес-изменения.
- Время показа полезных данных и число запросов реально сократились. Отдельно различать время первого ответа сервера и завершение загрузки данных.
- Веб-проверки и необходимые тесты гонок/изоляции проходят; ручная приемка владельцем на staging остается отдельным шагом.

## Что еще не доказано

Вклад медленных SQL, индексов, cold start, размера JS, обработки изображений и расстояния Vercel–Supabase не измерен. Vercel задан в sfo1; расположение staging-базы в этом исследовании не проверялось. Перемещать регион, добавлять индексы или виртуализацию без этих данных не предлагается.
