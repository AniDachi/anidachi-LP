# Daily Free 20: поэтапный план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Статус на 2026-10-30:** правила согласованы в пределах
[spec](../specs/2026-10-30-daily-free20-design.md). Выключенный блок 1А доставлен
в staging через PR #476 (`d1a422a9`), блок 2А — через PR #477 (`0e66cb45`).
Теперь отдельно согласован блок 2Б: сверка сохраненного и живого расхода,
тесты повторов/восстановления/UTC и доставка в staging без активации.
[Состояние блоков и доказательства](../../daily-free20-contract.md).
Подключение к действующим обработчикам, дизайн, включение Free20, production
и Store согласуются отдельно.
[Исходная передача](2026-10-30-daily-free20-handoff.md) остается историческим срезом.

**Цель:** 1 200 секунд совместного Free-хостинга в UTC-день с надежным событийным
учетом, сохранением действующих trial/paid-прав и двумя независимыми предложениями
40% на разных этапах жизненного цикла аккаунта.

**Архитектура:** существующие Supabase ledger/entitlements, Durable Object
room/metering/alarms, shared protocol и локальное отображение в расширении.
Не создавать отдельную систему местных суток, polling или новую P2P-архитектуру.

## Обязательный порядок

Перед **каждым** блоком ниже: объяснить scope, поведение, риски и проверки;
получить явное подтверждение; затем реализовать только этот блок и показать результат.
После принятия переходить к предложению следующего. Согласование правил не равно
разрешению сразу выполнить весь план.

Рабочий поток: актуальный staging → отдельная codex-ветка → PR в staging →
проверка и принятие → отдельно разрешенный promotion в main и выпуск Store.
Production, Stripe LIVE, публикация и изменение тестовых аккаунтов требуют
соответствующего отдельного разрешения. Не использовать старые разрешения другого релиза.

Дизайн согласуем после технического ядра локально/staging. До публичного включения
все пользовательские состояния должны быть правдивыми, понятными и проверенными.
Кампании возврата/удержания отдельные: не блокируют разработку ядра и не считаются
автоматически разрешенными вместе с ним.

## Неподвижные условия

- Новые trial заменяем Free20; уже начатые заканчиваются как обещано; paid не меняем.
- Общие 20 минут аккаунта: хост + гость, включая паузу; не расходуются хостом в одиночку.
- Сброс 00:00 UTC, без переноса остатка и без смены учетной зоны при поездке.
- Одно предупреждение, нет второго и нет post-quota hold/waiting_for_payment.
- Успешная серверно подтвержденная покупка снимает таймер живой комнаты;
  ее места/media остаются прежними. Ended generation не воскрешается.
- Free 4/4/4; новую history Free не записывает; старую не удаляем.
- Не заменять все 1800 на 1200: TTL и существующие технические grace независимы.
- Не очищать trial/anti-abuse/usage, не откатывать hostingActivationAt.
- Сохранить оптимизацию истории/People со staging. Новые адаптеры вне scope.
- Никаких quota-запросов/записей на каждый клиентский тик или playback heartbeat.
- Возврат из Stripe не доказательство покупки. Учет/авторизация на сервере.
- Две скидки допускаются последовательно, не одновременно на один платеж.

## Блок 1А. Первый согласованный локальный шаг

Подготовить отдельный версионированный формат времени хостинга, чистый parser/fence
и проверки legacy-совместимости. Существующие ответы/схемы и серверная выдача
остаются неизменными. Нет SQL, Stripe, UI, активации или доставки.

Это часть блока 1 ниже, а не завершение всех его пунктов. Runtime admission старых
клиентов, фактический Store-артефакт и once-per-account-day warning остаются открыты.
Запись реализации, тестов и rollback: [контракт](../../daily-free20-contract.md).

## Блок 2. Серверный учет аккаунта

**Плоскость:** web quota/entitlements, Supabase RPC/migrations при доказанной нужде.

- [ ] Сохранить UTC-ledger, накопительные ACK и защиту одного active host assignment.
- [ ] Разделить daily Free eligibility и исторический trial anti-abuse; новые trial
  запрещать только управляемой политикой, старые данные не стирать.
- [ ] Идемпотентная фиксация по account/room/generation/period; повторы и потеря ACK
  не списывают дважды, не дают больше 1200 и не возвращают уже использованное.
- [ ] При необходимости — forward-compatible миграция без reset/drop старого учета.
- [ ] Проверить две вкладки/устройства, пересоздание комнаты, late old-day ACK,
  UTC reset и новую комнату при pending settlement старой.

**Приемка:** корректный общий остаток и восстановление; никакого daily cron на всех
пользователей. SQL и окружения меняются только в отдельно разрешенном блоке.

### Блок 2А. Согласованный расчет по сохраненному расходу

- [x] Отдельный внутренний server reader на существующих account entitlements и
  `usage_daily`, UTC-день по времени authority из БД.
- [x] Free1200 минус подтвержденный расход; отсутствие нового trial или использованный
  trial не лишают Free дневного бюджета. Plus/Pro из действующих paid/trial/manual
  прав не получают дневной лимит; сроки и renewal не меняются.
- [x] Тесты остатка, исчерпания/overshoot, повторных чтений, владельца, UTC midnight,
  старого trial, текущего paid/manual и недостоверных данных.
- [x] PR #477 и проверка доставки в staging для блока 2А: CI, Web READY и
  post-switch smoke; DB workflow без миграций, production и Store не менялись.

Reader не вызывается текущими HTTP/WS/room handlers и не выдает право хостинга.
Его остаток учитывает только сохраненные секунды, не открытый интервал комнаты.
Это не снимок из 1А: live/ACK reconciliation, settlement и active-host assignment
не реализуются заново и не обходятся. Общий блок 2 и совместимость блока 1 пока
не завершены. Миграций, сброса учета, Stripe-операций и активации в 2А нет.

### Блок 2Б. Согласованная сверка сохраненного и живого расхода

- [x] Отдельный внутренний versioned checkpoint: owner/room/generation/sequence,
  UTC-период, raw account usage и ACK одного запроса после cumulative commit.
- [x] Выключенный web producer на существующих RPC и reader 2А; ошибка/неполный
  ACK/завершение комнаты не выдают дневной бюджет. Текущий SQL поддерживает только
  immutable room ID и generation 1; другой generation отклоняется до записи.
- [x] Чистая Worker-сверка с существующим meter: 7 сохраненных + 3 живых минуты
  дают 10 остатка до/после записи и потери ответа; сохраненный ACK нельзя потерять
  при восстановлении. Остаток в пределах дня не увеличивается при старых данных.
- [x] Тесты повторов, атомарного применения ACK, UTC, guest reconnect, paused
  playback и hibernation. Реальный DO проверен с тестовым лимитом 1200;
  действующие legacy 1800 cases сохраняются.
- [x] Финальные checks/review и PR #478: staging `5705743c`, Web/Worker READY,
  post-switch smoke, extension build #225. Production/Store/активация не менялись.

В границе 2Б функции не вызывались HTTP/WS/DO handlers. Это подготовленная цепочка
web→Worker, а не включенный новый учет. Existing serialized DO lifecycle,
checkpoint-before-I/O, settlement-before-release и проверка истечения старого дня
до rollover остаются обязательными условиями подключения. Новый SQL transaction,
ledger, polling и таймер не добавляются. Paid/unlimited не переводится в Free:
выдача нового time right и grant source относится к отдельному блоку 4.
Общие блоки 1–3 еще не завершены; wiring продолжен в отдельно согласованном 3А,
а включение и пользовательская приемка остаются впереди.

### Блок 3А. Согласованное выключенное runtime-подключение

Владелец разрешил подключить подготовленную сверку к циклу комнаты, проверить
сохранение запроса/ACK/остатка, restart/lost response/terminal и экономность,
затем доставить через PR в staging. Активация отдельно не разрешена.

- [x] Internal route с существующим service auth и strict protocol; один bounded
  callback возвращает budget и существующее подписанное media-разрешение.
- [x] `ANIDACHI_FREE20_ACCOUNTING_ENABLED` отсутствует по умолчанию; только точное
  `true` разрешает новый путь. Настройка не добавлена в реальные окружения.
- [x] В DO запрос+sequence+meter сохраняются до I/O; полный ACK и budget — одной
  SQLite transaction. Cache меняется после записи, policy KV восстанавливается
  по этой паре. При сбое более новый cumulative запрос покрывает предыдущий.
- [x] Проверки потери ответа, torn write, eviction, UTC во время callback,
  позднего старого expiry, host+guest/paused/reconnect и точных 20 минут.
- [x] В одинаковых 20 playback frames нет дополнительных budget callbacks,
  записей meter/Free20 state, KV или alarm. Один существующий alarm сохраняется.
- [ ] Полные checks/review и доставка 3А в staging; запись результата — в PR.

Это кандидат runtime, а не включенный новый продукт: room admission, новый
public HostingTimeSnapshot, live purchase/unlimited, UI и старые клиенты еще
требуют своих блоков. При неопределенности новый путь закрывает комнату и
сохраняет settlement до ACK; нового grace/payment hold нет. Старый warning на
5 мин в новом пути не выбирается. SQL account ledger и media/P2P не меняются.

## Блок 3. DO и экономный таймер

**Плоскость:** Worker/DO room-metering, room lifecycle, alarms.

- [ ] Начать интервал при host + guest; остановить при уходе host/последнего guest.
  Пауза видео расходует время, хост один — нет. Не менять playback/media heartbeat.
- [ ] Надежно сохранять activeSince/accumulation/pending result/terminal intent.
  Освобождать assignment только после корректного settlement.
- [ ] Один ближайший alarm: quota deadline/UTC rollover/обязательная проверка прав;
  warning deadline только если нужен по выбранному контракту.
- [ ] Sleep/hibernation/restart, duplicate alarm, reconnect, lost ACK, retry/backoff,
  delayed alarm после expiry и день без активности не ломают учет.
- [ ] Живая комната через UTC midnight продолжает с новым бюджетом; разделить расход
  точно по границе. Уже истекшая до нее не получает продление из-за задержки alarm.
- [ ] До/после измерить вызовы и записи на одинаковой сессии; исключить polling квоты.

**Приемка:** точность в пределах документированной server-liveness границы,
отсутствие лишних записей при неизменных условиях и сохраненная синхронизация.

- [ ] Проверить payment-vsquota0-vsUTC midnight, 3DS, failure, delayed/duplicate webhook,

- [ ] Проверить окончание старых trial/paid-прав в живой комнате по текущему контракту;

**Приемка:** нет состояния ожидания покупки после нуля, скрытого бесплатного времени,
потери оплаченного доступа или потери учета. Sandbox отдельно, LIVE без изменений.

остаются пустыми до выполнения соответствующего блока на актуальном коде.
