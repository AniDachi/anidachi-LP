## 1. Как читать статусы и источники

В этом документе используются четыре разных уровня, которые нельзя объединять
одной отметкой «готово»:

| Уровень | Что он подтверждает |
| --- | --- |
| Согласовано | Владелец подтвердил поведение продукта; это требование к реализации |
| Реализовано и проверено локально | Есть код, соответствующие тесты или локальная проверка сборки с указанными ограничениями |
| Принято на staging | Проверена реальная связка развернутых сервисов, Stripe TEST и нужных версий расширения |
| Выпущено и подтверждено | Проверены production, доступность Store-пакета, активация и результаты работы после нее |

На дату сводки у новой модели нет завершенной общей staging/production-приемки.
Записи о старых тестах относятся к указанным коммитам и условиям, а не к любой
будущей сборке. Этот документ составлен по текущим файлам и Git; внешние сервисы
при его подготовке заново не проверялись.

Приоритет правил: последние явно согласованные решения владельца → актуальные
спецификация и текущий статус → фактический код и доказательства проверки.
Расхождение кода с согласованным правилом требует исправления или обсуждения,
а не молчаливой замены правила. Исторические записи сохраняют контекст, но не
возвращают отмененные решения.

Два принципиальных изменения уже согласованы:

- Trial доступен любому Free без использованного trial. Первоначальное деление
  на новые и старые аккаунты отменено; дата регистрации больше не критерий.
- Старые Free-комнаты завершаются при переключении `T` без отдельного
  предупреждения и пяти минут ожидания. Первоначальный вариант `T + 5 минут`
  отменен только для этого разового перехода.

## 2. Согласованные правила продукта

### 2.1. Модель доступа

| Вопрос | Окончательное правило |
| --- | --- |
| Что остается у Free | Присоединение к комнате действующего Plus/Pro или trial-хоста; предусмотренные комнатой просмотр и взаимодействия |
| Создание своей комнаты | После активации только с собственным действующим paid/trial-доступом |
| Личная история Free | Новая запись запрещена; ранее сохраненная история, Resume и удаление остаются доступны |
| Trial | 3 дня, то есть 72 часа, для выбранного Plus или Pro с обязательной картой |
| Кто подходит | Новый или существующий Free, если аккаунт еще не использовал trial |
| Сколько trial | Один на аккаунт, общий для Plus и Pro |
| Когда начинается | После завершения оформления с картой и создания trial-подписки; не при регистрации, установке или открытии окна тарифов |
| После trial | Автоматическое продление в платную подписку, если пользователь не отменил продление |
| Отмена во время trial | Доступ до исходного окончания trial; затем Free, без первого регулярного платежа и без двухчасового ожидания |
| Смена Plus/Pro во время trial | Исходная дата окончания сохраняется; новый трехдневный период не начинается |
| Использованный trial | Следующее оформление предлагает обычную платную подписку, без повторных бесплатных дней |
| Существующая платная подписка | Продолжается на своих сроках и условиях; не заменяется новым trial |
| Цены | Берутся из настроенных Stripe Price IDs; переход сам по себе не устанавливает новые цены |
| Бесплатные 30 минут | После `T` собственного лимита Free-хостинга нет, как и обещания его обновления завтра |
| Лимиты гостя | Вместимость, камеры и микрофоны определяются комнатой хоста; новая личная квота Free-гостю не выдается |
| Право гостя писать историю | Определяется его собственной подпиской и разрешением записи, а не тарифом хоста |
| Согласие на историю | Существующее согласие и механизмы его соблюдения сохраняются |
| Коды планов | `free`, `plus`, `pro`; trial — состояние подписки, а не четвертый тариф |

Правило «один trial на аккаунт» не является обещанием одного trial на человека,
банковскую карту или устройство. Новые ограничения по этим признакам не были
согласованы и в данный переход не добавляются.

### 2.2. Три разных срока

| Срок | Назначение | Чего он не означает |
| --- | --- | --- |
| `T` | Серверный момент включения новой коммерческой модели и запрета Free-хостинга | Не дата регистрации и не момент обновления конкретного браузера |
| `trial_end` | Исходное окончание 72-часового trial конкретной подписки | Не сдвигается при смене тарифа, отмене/повторном включении продления или повторе запроса |
| `paymentPendingUntil` | Максимум `trial_end + 2 часа` для ожидания результата первого регулярного платежа при включенном продлении | Не новый trial, не гарантированные дополнительные два часа после подтвержденного отказа |

Обычная потеря paid/trial-прав имеет отдельное правило: новая комната и новая
запись истории запрещаются сразу, уже открытая платная/trial-комната получает
предупреждение и закрывается через пять минут. Это время завершения комнаты,
а не продление подписки или личной записи истории.

### 2.3. Что не входит в этот переход

Годовой план, счетчик людей, удаление согласия на историю, новые платформы,
надпись Coming soon для них и отдельная аналитическая страница остаются за
рамками. Не требуется менять media protocol ради paywall, полностью переделывать
дизайн сайта или обновлять Stripe SDK без отдельной необходимости.

Существующие правила возвратов и повторных платежей действующих платных
подписок отдельно не перерабатываются. Любое новое продуктовое правило сначала
обсуждается с владельцем.

## 3. Что произойдет с существующими пользователями

| Пользователь или состояние в момент перехода | Ожидаемое поведение |
| --- | --- |
| Зарегистрированный Free, trial не использован | Аккаунт сохраняется. Может бесплатно присоединяться; для собственной комнаты добровольно оформляет trial Plus/Pro с картой |
| Новый Free после запуска | Проходит тот же путь; регистрация сама по себе не включает trial и не создает подписку |
| Free с уже использованным trial | Может присоединяться; собственный хостинг требует обычной оплаты |
| Действующий Plus/Pro | Оплаченный срок, подписка, Stripe customer/subscription и данные сохраняются; второй checkout для новой подписки не создается |
| Действующий trial при повторном деплое или восстановлении | Сохраняются исходные даты, использованность trial и выбранные права; повторная поставка ничего не перезапускает |
| Аккаунт с существующим ручным доступом | Существующая логика server-side manual grants сохраняется; переход не обнуляет такие права |
| Free с ранее сохраненной историей | Может читать, продолжать видео и удалять сохраненное; новый прогресс во время Free не записывается |
| Free-гость в платной/trial-комнате | Продолжает просмотр по правилам комнаты; собственных 30 минут и права записи истории от хоста не получает |
| Хост открытой комнаты, созданной как Free | Эта комната входит в закрытие при `T`; счетчик или старое расширение ее не продлевают |
| Гость открытой Free-комнаты | Теряет доступ к закрываемой комнате вместе с остальными участниками; причина связана с комнатой, не обязательно с его личным тарифом |
| Хост Free-комнаты успел купить Plus/Pro до `T` | Старый замороженный тип комнаты не меняется. Для платного хостинга создается новая комната после штатного освобождения прежней активной сессии |
| Уже открытая paid/trial-комната | Не включается в массовое закрытие только из-за перехода модели; продолжает подчиняться обычным правилам своего хоста |
| Пользователь вернулся через несколько дней со старым кешем | Права и допуск сверяются с сервером; старый кеш не возвращает бесплатное создание или запись |
| Пользователь остался на старой Store-версии | Серверный запрет действует независимо от обновления. Понятность отказа, join/reconnect и остановка медиа должны быть приняты на точной старой сборке |
| Пользователь установил unpacked ZIP | Обновляет сборку вручную; это отдельный канал, не автоматическое обновление из Store |
| Пользователь сохранил старую ссылку Checkout | Ее условия и итог нужно сверить; несовместимая открытая сессия должна быть безопасно завершена до нового предложения. Уже состоявшуюся оплату нельзя потерять |
| Продление trial отменено | До исходного конца остается выбранный доступ, затем Free без ожидания нового платежа |
| Оплата прошла поздно после возврата на Free | Подтвержденный доступ восстанавливается; новый trial, история за пропущенный период и уже завершенная комната не восстанавливаются |

Переход не требует повторной регистрации, удаления истории или массового
пересоздания подписок. Существующий Free не становится плательщиком автоматически:
карта и оформление требуют его действий.

## 4. Путь пользователя и жизненный цикл подписки

### 4.1. Создание комнаты пользователем Free

1. Пользователь видит обычную кнопку создания комнаты.
2. После клика сервер проверяет реальное право на хостинг.
3. Если ответ — `403 HOST_SUBSCRIPTION_REQUIRED`, расширение открывает объяснение:
   присоединяться можно бесплатно, для собственной комнаты нужен Plus или Pro.
4. Подтвержденная сервером eligibility позволяет предложить один трехдневный
   trial с картой. Если trial уже использован, предлагается обычная оплата.
5. При неизвестных правах интерфейс предлагает проверить условия, не обещая
   бесплатный период и не утверждая, что пользователь его уже использовал.
6. Переход на тарифы происходит только по кнопке пользователя. Закрытие окна,
   Escape и возврат из другой вкладки ничего не покупают и не создают комнату.
7. После оформления расширение обновляет отображение прав. Пользователь явно
   нажимает создание комнаты снова; автоматического создания после Stripe нет.

Серверный сбой не является доказательством Free и не должен открывать ложный
paywall. До `T` совместимая версия сохраняет прежний разрешенный сценарий.

### 4.2. Состояния подписки

| Состояние | Хостинг и личная запись | Отображение и действие |
| --- | --- | --- |
| Не авторизован | Нет подтвержденного личного доступа | Вход в аккаунт; персональный trial еще не обещается |
| Free, trial доступен | Нет собственного хостинга и новой истории | Предложение выбрать Plus/Pro и оформить trial с картой |
| Free, trial использован | Те же ограничения Free | Обычная платная подписка |
| Оформление открыто, но не завершено | Само открытие не выдает новых прав | Можно вернуться к согласованной сессии; trial не считается использованным только по открытию |
| Trial создан | Права выбранного Plus/Pro до исходного конца | Дата окончания, будущая цена/период, управление продлением |
| Trial отменен, срок еще идет | Права до того же исходного конца | Ясно показать отмененное продление и дату потери доступа |
| Trial закончился, ожидается первый платеж | Права сохраняются до результата, максимум до `trial_end + 2 часа` | Состояние обработки; не сообщение об оплаченном месяце |
| Первый платеж подтвержден | Права на подтвержденный период | Оплата отделена от факта начала trial |
| Карта отклонена или требуется действие/3DS | Прекращение ожидания; возврат на Free | Понятное предложение завершить оплату; отдельное штатное закрытие текущей комнаты |
| Два часа истекли без подтверждения | Free | Новый хостинг/запись запрещены; поздняя оплата обрабатывается отдельно |
| Подтвержден поздний платеж | Восстановление оплаченных прав | Без нового trial и без заполнения истории за Free-период |
| Недоступна проверка прав | Не выдавать права из предположений | Временная ошибка; не объявлять ее отказом карты или использованным trial |

Система не должна выдавать оплаченный месяц только по строке `active` в Stripe
или по возврату пользователя на success URL. Начальный нулевой счет trial и
первый регулярный счет — разные события.

### 4.3. Точная граница отмены и смены тарифа

Отмена продления до конца trial сохраняет доступ до исходного конца и исключает
двухчасовое ожидание. Повторное включение продления до этого конца не меняет
дату. Смена Plus/Pro не сбрасывает использованность, даты или отмену продления.

Перед подтверждением смены показываются новый тариф и его цена. Если условия
или состояние подписки изменились между показом и подтверждением, требуется
актуальная проверка. Опоздавший запрос после окончания trial не должен применять
устаревшие trial-параметры. Конкурирующая отмена и смена тарифа требуют отдельной
сквозной проверки; локальный тест одного запроса не закрывает эту гонку.

## 5. Распределение ответственности в системе

| Часть системы | Ответственность |
| --- | --- |
| Stripe | Карта, подписка, счета, платежи и их подтвержденные состояния |
| Web + Supabase | Проверенное зеркало подписки, использованность trial, эффективные права, комнаты, история и транзакционные ограничения |
| Worker + Durable Objects | Допуск в живую комнату, WebSocket, sync/signaling, закрытие, долговечное восстановление завершения |
| Расширение | Отображение серверных прав, пользовательские действия, локальный плеер и медиа, соблюдение разрешений личной истории |
| Общий protocol | Совместимые схемы, коды ошибок и данные, которые пересекают границы компонентов |

Расширение не решает право на trial по возрасту аккаунта, локальным часам,
сохраненному `planCode` или параметрам URL. Сервер не принимает присланные
клиентом `eligible`, длительность trial и дату окончания как разрешение доступа.

Метаданные хостинга добавляются совместимо к существующему ответу аккаунта:
владелец, серверное время, версия/момент активации политики, `canHost`, eligibility
и данные trial. Отсутствующие поля старого ответа означают отсутствие достоверного
знания, а не автоматический trial. Значение `existing_account` допускается для
чтения старого payload; новая логика не возвращает возрастной отказ.

Разделение ошибок обязательно:

| Ответ | Смысл |
| --- | --- |
| `403 HOST_SUBSCRIPTION_REQUIRED` | Подтвержденный коммерческий отказ в собственном хостинге |
| `503` при недоступной authority | Временный сбой проверки; не предложение купить тариф |
| `404`/терминальный отказ комнаты | Комнату нельзя восстановить повтором старой сессии |
| `426` у снятого с поддержки history endpoint | Требуется совместимый клиент; не успешное создание и не обычный paywall |
| `QUOTA_EXHAUSTED` | Прежний сценарий квоты; не причина отказа нового Free-хостинга после `T` |

Старые обязательные payload-поля, существующие причины завершения и необходимые
legacy consumers сохраняются до доказанной возможности их удалить.

## 6. База данных и сохранение существующих данных

### 6.1. Что требуется хранить

- Коммерческую политику с ревизией, серверным `T` и отдельным управлением
  доступностью новых trial. Начальное состояние миграции неактивно.
- Одну долговечную запись trial на аккаунт, общую для Plus/Pro: связь с Stripe,
  исходные даты, факт использования, состояние первого платежа.
- Резервирование оформления, идентичность операции и результат сверки Stripe.
- Проверенное состояние прав, согласованное с существующей историей и доступом.
- Операцию переключения и полный устойчивый список комнат для закрытия.
- Отдельные подтверждения запрета живой работы комнаты и окончательного учета.

Исходная идентичность trial и его конец не должны свободно перезаписываться
runtime-клиентом. Учитываются RLS, SQL constraints, владение subscription и
права выполнения RPC. Оператор включает коммерческую политику; обычный запрос
приложения не получает такого полномочия. Для окончательной версии trial-записей
используется разрешенный RPC-путь; ранний тест прямой вставки описывает только
исторический foundation checkpoint.

### 6.2. Подготовленная цепочка миграций

Ниже перечислены файлы текущей локальной реализации; наличие файла не означает,
что он применен в staging или production:

1. `20260927131509_paid_hosting_trial_foundation.sql` — политика и учет trial.
2. `20260927132751_subscription_checkout_reservations.sql` — резервирование checkout.
3. `20260927134951_stripe_trial_lifecycle.sql` — жизненный цикл и запись подтвержденных состояний.
4. `20260927144056_paid_hosting_room_admission.sql` — транзакционные проверки комнат.
5. `20260927155330_paid_hosting_cutover_delivery.sql` — операция переключения, очередь закрытия и восстановление.
6. `20260928083738_unified_free_trial_eligibility.sql` — единое право неиспользованного trial для Free любого возраста.

Последняя миграция обязательна в поставке: частично обновленный сервер не должен
оставаться со старым правилом «только новые аккаунты». Уже разделяемые миграции
не переписываются ради удобства дальнейшего выпуска; перед поставкой сверяется

### 6.3. Что сохраняется и как это доказывается

Сохраняются пользователи, авторизация и связи аккаунтов, Stripe customer и
subscription IDs, оплаченные сроки, история, настройки согласия, текущие связи
комнат и участников, ограничения активных сессий, накопленный учет использования
и защита от устаревшей записи истории.

Миграции проверяются на заполненной изолированной базе, а не только на пустой.
Сравниваются содержимое важных таблиц и ограничения до/после, роли и реальные
конкурирующие транзакции. Дополнительно проверяется неактивность новой политики
и отсутствие созданных команд закрытия при обычном применении схемы.

Перед production требуется проверенный способ восстановления данных и
совместимый runtime. Старые разрешения на сброс тестовых данных до запуска
сервиса не разрешают очищать нынешнюю production-базу. Локальные синтетические
данные не являются доказательством проверки всех реальных production-записей.

`personal_history_policy.active` — отдельная политика. Ее выключение может
вернуть прежние пути записи истории и не является откатом платного хостинга.

## 7. Оформление подписки и защита от повторов

### 7.1. Нормальный путь

Сервер проверяет сессию пользователя, владение аккаунтом, выбранный Plus/Pro,
действующую подписку и текущую eligibility. Действующая подписка ведет в управление,
а не создает вторую. Подходящий Free получает trial с обязательной картой;
использованный trial — обычное оформление.

До обращения к Stripe создается долговечный резерв. Для повторов сохраняются
идентичность операции, параметры предложения и idempotency key. Подходящая уже
созданная сессия переиспользуется. Разные одновременные запросы одного аккаунта
не должны создавать две независимые подписки.

### 7.2. Обязательные пограничные случаи

| Случай | Требуемая обработка |
| --- | --- |
| Двойной клик или две вкладки | Один согласованный результат оформления |
| Ответ Stripe потерян после создания сессии | Сверка той же операции; отсутствие ответа не доказывает отсутствие сессии |
| Повтор после истечения надежного окна idempotency | Остановка для сверки, если прежний результат неизвестен; не создание вслепую |
| Брошенное оформление | Само по себе не расходует trial; резерв освобождается только после проверки итога |
| Отмена/истечение сессии одновременно с оплатой | Подтвержденное завершение имеет приоритет; оплаченная подписка не теряется |
| Пользователь меняет выбранный тариф | Предыдущая несовместимая сессия сверяется и безопасно закрывается; новая соответствует показанным условиям |
| Старый Free начал оформление без trial до перехода | Нельзя молча вернуть устаревший checkout вместо нового предложения |
| Пользователь открыл старую сохраненную Stripe URL напрямую | Нужна глобальная обработка старых открытых ссылок при активации; проверки только нового `/create-checkout-session` недостаточно |
| Ошибка при подтверждении истечения старой сессии | Не создавать второй checkout до достоверной сверки |
| Смена аккаунта во время оформления | Поздний ответ прежней сессии не меняет состояние другого входа |

В текущей локальной реализации неопределенный повтор старше 23 часов без
идентифицируемой Stripe-сессии останавливается для сверки. Это техническая
защита конкретного кода, а не дополнительное продуктовое ограничение trial.

**Открытый пункт:** обработка отдельного аккаунта реализована и проверена,
но глобальная процедура закрытия несовместимых старых checkout-ссылок перед
активацией еще требует завершения и доказательства полноты. Завершенные платежи
не отменяются такой процедурой и не заменяются trial.

## 8. Платежные события и смена тарифа

Webhook и ручная синхронизация должны сохранять проверку подписи, владельца и
свежести данных. Старый ответ не перезаписывает более новое состояние; повтор
или перестановка событий не начинают новые 72 часа или новое окно ожидания.

Проверяются как минимум:

- создание trial и его начальный нулевой счет;
- первый регулярный счет, его подтвержденный период обслуживания и результат;
- успешный платеж, отказ карты и необходимость дополнительного действия;
- потерянное, повторное и пришедшее поздно событие;
- событие отмены, когда другой запрос уже читает подписку;
- старое failure-событие после подтвержденной оплаты;
- восстановление после поздней оплаты без нового trial;
- отсутствие нового полного месяца только из-за статуса `active`;
- точная граница исходного `trial_end + 2 часа` и отсутствие этого ожидания
  после отмены продления.

Даты прав выводятся из актуального подтвержденного состояния и нужного периода
счета. В ранее проверенном sandbox период строк счета отличался от его общего
назад направленного `period_start`; это учитывается в реализации, а не заменяется
предположением «оплатил сейчас — дать месяц от текущей даты».

Для смены тарифа во время trial выбран серверный путь quote/confirm с проверкой
владельца и защиты запроса. Он сохраняет исходный `trial_end`, отсутствие
пропорционального досрочного списания (`proration_behavior=none`) и состояние
отмененного продления. После изменения выполняется защищенная синхронизация.

Причина этого выбора: проверенная ранее конфигурация sandbox Portal не
соответствовала согласованной смене тарифа с сохранением trial. Нельзя просто
включить там поведение, обрывающее trial. Конфигурация конкретной среды должна
проверяться перед выпуском заново.

Цена в quote сейчас является месячной ценой тарифа. Существующие скидки, налоги
и credits Stripe сохраняются, поэтому месячную цену нельзя выдавать за точно
рассчитанный итог будущего счета. Интерфейс должен явно различать эти значения.

Ранее обнаружено, что remote webhook не подписан на
`invoice.payment_action_required`; регистрационный скрипт уже учитывает событие.
Фактическое обновление списка событий в целевой среде и поступление webhook
остаются частью настройки и staging-приемки.

## 9. Серверные проверки комнат

Проверка требуется не только на кнопке, но во всех серверных путях создания,
возврата уже созданной комнаты, получения допуска и продления:

- обычный `POST /api/rooms`;
- повторный запрос с тем же идентификатором;
- прямые SQL RPC и поддерживаемые legacy wrappers;
- host connect/reconnect и выдача/обновление room token;
- создание или восстановление через старые пути истории;
- запрос, начавшийся до `T`, но дошедший до вставки комнаты после `T`;
- старый подписанный JWT и пробуждение спящего Durable Object.

Право хоста и право гостя различаются. Free-гость допускается к действующему
paid/trial-хосту, но не получает собственное право создавать комнату или писать
историю. Существующее ограничение активной сессии и лимиты комнаты сохраняются.

Нужна транзакционная проверка с согласованным порядком блокировок. Иначе запрос,
прошедший предварительную проверку до переключения, может создать запрещенную
комнату после него. В текущем коде есть дополнительная проверка при вставке;
локально проверены реальная граница времени и параллельные запросы.

Каждое WebSocket-подключение, включая старый JWT, сверяет актуальное серверное
состояние. После ожидаемых сетевых операций Worker повторно проверяет локальное
закрытие, чтобы ответ допуска, полученный с задержкой, не открыл уже закрытую
комнату. При недоступной проверке применяется временный отказ, а не старые права.

## 10. Переключение модели и закрытие старых комнат

### 10.1. Что именно означает переключение

Выбран подход: сначала совместимые схема, серверы и клиент, затем отдельная
активация новой политики. Деплой кода не должен сам закрывать комнаты или
включать trial. Операторский запуск записывает единственную ревизию и серверное
UTC-время `T`.

Для массового закрытия берется тип комнаты, замороженный при создании:
`host_plan_code=free`, включая подтвержденные старые бесплатные эквиваленты
вроде `watcher`. Текущий апгрейд аккаунта не превращает старую комнату в paid.
Действующие paid/trial-комнаты в этот список не включаются.

### 10.2. Атомарная операция в базе

Одна транзакция блокирует политику в согласованном с admission порядке,
фиксирует `revision/T` и создает полный список заданий закрытия. Создание комнаты
либо завершается по прежним правилам и попадает в список, либо проверяет уже
новую политику и получает отказ. Между этими путями не должно оставаться окна.

У операции есть заранее сохраненный идентификатор. Если результат commit
неизвестен, сначала читается эта операция и повторяется она же. Новый `T` или
новый идентификатор из-за timeout не назначаются. До commit нет исполняемых
будущих команд; отмененная подготовка ничего не закрывает.

### 10.3. Доставка и подтверждение

После commit долговечная очередь в базе доставляет команды Web → Worker.
Идентичность включает ревизию, комнату и ее поколение; `closingAt=T` сохраняется.
Доставка не зависит от открытого терминала, посетителя сайта или одного
неподтвержденного запроса.

Worker сначала долговечно фиксирует запрет дальнейшей работы комнаты, затем
отправляет совместимое завершение и закрывает соединения. Это работает и для
legacy-комнаты без `roomPolicy`/media lease. Блокируются новый admission,
sync/signaling и автоматические heartbeat-ответы.

Окончательный учет, доставка связанных данных, освобождение active assignment
и локальная очистка — отдельные подтверждаемые стадии. Ошибка callback не
должна оживлять комнату или терять учет. Нельзя заранее массово поставить
`rooms.status=ended`, пропустив штатный finalization.

Потеря ACK допускает повтор, но не двойной учет. Позднее завершение старой
комнаты не должно удалить назначение уже созданной новой paid-комнаты.
Доставка хранится до подтверждения, без лимита попыток или удаления по expiry.

### 10.4. Восстановление и текущие технические параметры

В локальной реализации используется Supabase Cron + pg_net → закрытый Web drain,
а у Worker — самостоятельное повторное планирование в существующем общем alarm.
Recovery по умолчанию выключен. Перед включением проверяются адреса, ключи,
защита staging и фактическое прохождение всей цепочки.

| Параметр текущей реализации | Значение и смысл |
| --- | --- |
| Параллельная обработка Web drain | До 4 целей |
| Аренда задания | 60 секунд; не меняет срок закрытия комнаты |
| Бюджет одного прохода | 35 секунд |
| Ограничение запроса доставки | 28 секунд |
| Ограничение операции базы | 2 секунды |
| Recovery Cron | Раз в минуту для ожидающих работу целей |
| Застрявшая транспортная очередь | Сверка после 90 секунд; требует восстановления транспорта, без удаления долговечного задания |
| Собственный retry Worker | 30 секунд; сохраняет работу после сна, перезапуска и длительного сбоя |

Эти числа описывают существующий локальный код. Они не являются принятым SLA
production-закрытия. Фактическая допустимая задержка под нагрузкой еще должна
быть измерена и принята на staging.

Ключ drain отдельный для каждой среды и дает только право запустить обработку
очереди. Он не дает вызывающему выбрать произвольную комнату, не заменяет ключ
допуска и не заимствует полномочия у системы уведомлений.

### 10.5. Доказательство завершенного переключения

`T` — начало действия политики, а `fencedAt` и `finalizedAt` — наблюдаемые
моменты запрета работы и окончательного учета. SQL commit и отключение всех
WebSocket в другом сервисе не являются одной атомарной операцией. Нельзя
записывать желаемый deadline вместо фактического времени выполнения.

Переход принят только когда сверены полный список целей, запрет работы каждой
комнаты, finalization, освобождение ее назначений и отсутствие пропущенных
Free-комнат. Неподтвержденные цели означают незавершенный запуск. P2P-поток может
существовать отдельно от signaling, поэтому остановка сигнализации сама по себе
не доказывает, что камера и звук прекратились в старом клиенте.

### 10.6. Нерешенный случай старой завершенной комнаты

У старого Worker может быть terminal tombstone — сохраненная запись завершения —
без нового достоверного подтверждения запрета работы. Сейчас такой случай
возвращает `ROOM_TERMINAL_PROOF_UNAVAILABLE`: комната остается закрытой,
задание остается неподтвержденным. Система не выдумывает время закрытия.

До приемки нужно доказать отсутствие такого состояния среди реальных целей
или реализовать проверенное восстановление по точной комнате, поколению,
исходному учету и активной сессии. Удалять проблемную цель из очереди нельзя.
Предыдущая попытка автоматически повторить завершение была отклонена
автоматической проверкой разрешений из-за риска повредить учет/сессию при
неверной связи старой записи; изменение не применялось. Этот вопрос остается
открытым, а сохраненный безопасный отказ проверен тестом.

## 11. Все необходимые изменения расширения

### 11.1. Карта действий

| Поверхность | Что требуется |

| Обычная Create room | Сохранить привычную кнопку; серверный коммерческий отказ открывает окно тарифов |

| Вход по приглашению/room hash | Подключать к существующей комнате через admission; не подменять join созданием |

| Reconnect | Повторять только допустимую попытку подключения; терминальные ответы останавливают восстановление |
| Resume истории | Открывать подходящее видео и сохраненную позицию; не создавать комнату и не выдавать право записи |

| Предупреждение обычной потери paid-прав | Показывать исходный серверный deadline один раз; повторные события не дают новые пять минут |
| Logout/login и другой аккаунт | Удалять устаревшие предложения, ответы и подготовленную сессию; не переносить чужую историю |

### 11.2. Удаление Free-квоты без поломки совместимости

Нельзя просто заменить `dailyHostSeconds: 1800` на `0` или `null`: в прежней
policy `null` означает отсутствие лимита. После `T` выключается новый Free
сценарий, а legacy schema/usage сохраняются для работы до переключения и
окончательного учета старых комнат.

Успешный старый quota v1 не расширяется несовместимыми полями. Post-T Free
endpoint отвечает `403 HOST_SUBSCRIPTION_REQUIRED` без чтения usage. Временная
ошибка authority остается `503`. Расширение использует подтвержденные hosting
metadata и серверное время; отсутствие ответа не считается новой политикой.

Нужно исключить возврат счетчика после позднего ответа, старого кеша, смены
аккаунта, первого открытия, UTC-полуночи, reload и полного перезапуска браузера.
У Free-гостя просмотр дольше 30 минут не расходует собственную квоту.
Технические room-token TTL, heartbeat и lease timers не удаляются вместе с
коммерческим счетчиком. Отдельный постоянный опрос вместо существующего
обновления при focus/visibility не вводится без необходимости.

### 11.3. Сессии, ошибки и завершение

После отказа создания освобождаются подготовленная сессия и блокировка вкладки
Web Lock. Ручная повторная попытка должна работать. Поздний ответ от предыдущего
входа, даже того же аккаунта с похожим token, не открывает paywall в новом входе.

Гостю закрытой комнаты не показывается предложение оплатить собственный тариф
как способ восстановить чужую комнату. Терминальные HOST/404/426 очищают recovery
состояние без бесконечного retry. Объяснение не исчезает из-за auth refresh.

Для нового объяснения cutover используется совместимое добавочное
`hostingCutover: true` при прежней причине `capability_expired`. Маркер приходит
из достоверного состояния закрытия комнаты, не выводится из тарифа гостя.
Более раннее закрытие сохраняет свою причину. При потере события и одном close
4004 используется нейтральное объяснение, без выдуманного отказа оплаты.

Проверяются обычная страница, popup, шторка, fullscreen, узкий экран, клавиатура,
Escape и восстановление фокуса. Локальные скриншоты отдельных состояний не
заменяют приемку полного интерфейса на финальном артефакте.

## 12. История просмотров и смена аккаунта

Право читать историю и право записывать новый прогресс разделены. Для чтения
нужны собственные действующие разрешения чтения; наличие старого частного кеша
само по себе не разрешает его показать другому входу.

Free сохраняет чтение, Resume и удаление записанного. Popup использует прежний
переход Manage history; новая функция удаления в popup не добавляется.
Редактирование/новая запись прогресса продолжают требовать предусмотренного
платного доступа. Текст должен объяснять остановку записи, не потерю всей истории.

Личный capture/controller/writer проверяет владельца, поколение входа, согласие
и срок capture lease. Комнатная authority хоста не продлевает личную lease гостя.
При подтвержденном Free или истечении разрешения новая запись прекращается;
поздний ответ не оживляет закрытый период записи. После возвращения платного
доступа учитываются текущие наблюдения, без backfill времени Free.

Временная недоступность сервера отличается от подтвержденной утраты прав:
нельзя продолжать запись за пределами разрешения, но нельзя без основания
удалять уже допустимую очередь или сохраненные данные. Исходные consent,
account-generation и access fences сохраняются.

Resume привязан к владельцу, поколению, источнику и ограниченному времени.
Неверный источник, другой аккаунт, новая комната или истечение intent прекращают
устаревший seek. Сам Resume не отправляет запрос создания комнаты.

Отдельно защищена групповая история: durable membership не равен текущему
нахождению в комнате. Приглашение после ухода, новое pending-приглашение и его
принятие не должны задним числом приписывать пользователю чужой просмотр.
Исправление устаревшего тестового setup не меняло это продуктовое правило.

перед выпуском; обещание собственного письма за 24 часа не добавляется без
реально существующего механизма.

## 14. Старые версии и выпуск через Chrome Store

### 14.1. Матрица совместимости

| Клиент | До `T` | После `T` |
| --- | --- | --- |
| Новый, совместимый | Старые правила хостинга и квоты продолжают работать | Серверные новые права, окно тарифов, отсутствие Free-квоты |
| Старый опубликованный Store-клиент | Прежнее поведение | Free create запрещен сервером; paid/trial join и штатное закрытие должны быть проверены на точном пакете |
| Уже открытая вкладка старой версии | Продолжает текущую сессию по прежним правилам | Серверные запреты действуют; обновленный UI может требовать обновления расширения/перезагрузки страницы |
| Unpacked staging ZIP | Использует только тестовую среду | Обновляется вручную; не заменяет Store-клиент в проверке совместимости |
| Старый и новый клиент в одной paid-комнате | Совместный просмотр | Проверяются join, reconnect, sync, камера, микрофон и завершение |

Проверка старого parser по исходнику полезна, но не равна проверке установленной
опубликованной версии. Нужны точные version, manifest, SHA-256 и происхождение
пакета. Метаданные публичного legacy ZIP также не доказывают байты Store-пакета.

Сохранение бесплатного хостинга только старым версиям не предусмотрено:
политику контролирует сервер. Ожидание обновления всех установок тоже не является
условием активации. Принудительный reload расширения посреди просмотра не выбран
обычной стратегией выпуска.

### 14.2. Требования к новому пакету

- Та же production-карточка: `gpkolofebdhfpapbbgdkdkmlmjfidgmn`.
- Manifest version выше фактически опубликованной; версия подтверждается в Store,
  а не только по локальному `package.json`.
- Production endpoints и узкие разрешения; staging/экспериментальный ZIP не
  отправляется как production-пакет.
- Зафиксированные source commit, build channel, версия и SHA-256.
- ZIP и сгенерированные папки не коммитятся как исходники.
- Материалы проверки объясняют trial и оплату; проверяющему предоставляется
  воспроизводимая проверка платного пути с изолированными тестовыми правами,
  без клиентского обхода paywall и требования оплачивать из своих средств.

Отправка предусматривает deferred publishing. Одобрение и публичная доступность
различаются. Сначала подтверждается доступность опубликованной новой версии,
затем выполняется согласованная активация. Если Store задерживает публикацию,
переносится `T`, а не включается модель по неподтвержденному календарному обещанию.
Текущие условия и допустимое окно отложенной публикации сверяются перед отправкой.

### 16.4. Уровни проверки и команды

Сначала проверяются SQL/HTTP/компоненты, затем неизмененная собранная extension,
затем реальные сервисы staging и два профиля/нужные версии клиента. Отдельно
выполняется репетиция активации и восстановления. Для media/закрытия проверяются
не только сообщения, но и реальный звук/видео.

В соответствии с измененными частями используются `pnpm check`, `pnpm test`,
web/API/extension/protocol checks и tests, disposable SQL-набор и конкурентные
контракты, Worker runtime, `pnpm harness:rooms`, реальный локальный WebRTC harness,
`pnpm build:extension:staging`, `pnpm validate:extension:staging`,
`pnpm smoke:worker:staging` и `pnpm dev:check`.

Сборка и проверки привязываются к точному commit. При обычной ручной проверке
используется выделенный Chrome AniDachi Test. Локальная автоматизация в отдельном
профиле не должна менять повседневный профиль пользователя. Правила выбора
проверок — в [quality gates](../../development-quality-gates.md).

## 19. Порядок дальнейшей работы и запуска

### 19.1. Завершить согласованную локальную подготовку

1. Сверить текущий Git/source с последними решениями; сохранить существующую работу.
2. Принять минимальные pricing/success/billing; сверить localhost/test-настройки
   и пройти настоящий Checkout/возврат/billing, не подменяя эту проверку fixtures.
3. Вместе с владельцем согласовать оставшиеся тексты/поверхности и визуальную
   доработку; показывать настоящий интерфейс локально.
4. Закрыть локальные дефекты и уточнить O03/O04; не переносить неопределенное
   поведение в выпуск под видом законченной реализации.
5. Проверить весь diff, межкомпонентные контракты и необходимые тесты.
6. Собрать итоговый узкий staging ZIP из проверенного commit и записать identity.

Пока действует согласованная граница: локальная работа без push и изменения
staging/production. Настоящий staging-переход начинается после отдельного
согласования. Локальный показ сайта не меняет опубликованный продукт.

### 19.2. Поставка и репетиция на staging

Нормальный Git-путь: `codex/* → PR в staging → приемка → promotion PR в main`.
Прямой push в `main` и force-push общих веток не используются.

Порядок компонентов принципиален:

1. Добавочные миграции, новая политика и recovery еще выключены.
2. Совместимый Web с admission/drain и нужной схемой.
3. Worker, который зависит от нового admission endpoint.
4. Проверка прежнего поведения при неактивной новой модели.
5. Новый тестовый клиент, правильный Stripe TEST и настройки recovery.
6. Репетиция активации на тестовых данных, вся матрица пользователей/версий.
7. Репетиция отмены подготовки, неопределенного commit, сбоев и восстановления.
8. Release receipt с deployments, migrations, artifact hashes, результатами и
   ограничениями; приемка владельца перед production promotion.

Новый Worker нельзя выпускать раньше работающего Web admission: иначе
обязательная проверка допуска может временно остановить все новые подключения.

### 19.3. Совместимый production и проверка Store

После принятого staging подготовить данные/восстановление, пройти promotion PR,
поставить совместимые схему и серверы с выключенной новой моделью и проверить
прежний product flow. Сверить LIVE и точные версии, затем собрать production ZIP.

Подготовить listing, инструкции и тестовый доступ для проверки, отправить пакет
с отложенной публикацией. Дождаться одобрения и согласовать окно запуска.
Отправка, публикация и активация — разные действия, каждое с собственным результатом.

### 19.4. Публикация и единая активация

До commit обязательны: принятые O01–O08, доступность runner/recovery, совместимый
путь восстановления, действительные LIVE-настройки и проверенные данные целей.

1. Опубликовать одобренный пакет и проверить его фактическую доступность.
2. При задержке публикации остановиться до активации; не выбирать новый обходной
   способ включить trial на неподготовленных клиентах/серверах.
3. Выполнить одну операторскую транзакцию с сохраненным operation ID и `T`.
4. Проверить отказ Free create, paid/trial create, Free join, соответствующие
   тексты сайта и расширения и начало trial через новый путь.
5. Сверить все цели, fence/finalization и назначения, измерить задержки.
6. Если есть pending/неопределенные результаты, продолжать восстановление и
   считать запуск незавершенным до подтверждения.

Обновление 100% Chrome-установок не ожидается. Закрытие старых Free-комнат
выполняется без специального пяти­минутного предупреждения, но фактическая
сетевая задержка измеряется и не скрывается.

| --- | --- |
| До commit активации | Отменить подготовку; не должно существовать исполняемых будущих закрытий |
| Неизвестен результат commit | Прочитать сохраненную операцию, продолжить ее; не создавать новый `T` |
| После `T` часть доставки не завершилась | Восстановить транспорт/сервис и продолжить прежние задания с исходной идентичностью |
| Требуется откат кода | Только на проверенную версию, понимающую новую схему, trial и terminal state |
| Нужно остановить новые trial | Отдельное управление новыми оформлениями; уже выданные trial и оплаченные права сохраняются |
| Ошибка в расширении | Совместимое серверное восстановление; обновление Store распространяется не мгновенно |

Откат не стирает trial ledger, не возвращает eligibility использовавшим trial,
не отменяет реальные платежи/подписки, не удаляет историю и не воскресает
завершенные комнаты. Неподтвержденная очередь закрытия не отбрасывается.
Исторический billing-код без trial-границ не является безопасным кандидатом
восстановления после выдачи trial.

Возврат бесплатного хостинга — отдельное продуктовое решение владельца,
а не технический побочный эффект rollback. Очистка legacy-кода, квоты и
временных механизмов допустима отдельным этапом после принятой активации,
завершения старых комнат и проверки поддерживаемых клиентов.

## 21. Наблюдение после запуска и ведение прогресса

### 21.1. Что наблюдать

Используются существующие средства наблюдения, без добавления новой страницы
аналитики в этот объем:

- ошибки и результат Checkout по версиям клиента/средам;
- успешность синхронизации подписок и запаздывание webhook;
- число начавшихся trial отдельно от первых подтвержденных регулярных платежей;
- отказ Free create и успешность paid/trial create и Free join;
- отсутствие старой Free-квоты и ошибок восстановления комнаты;
- доля неподтвержденных закрытий, фактическая задержка, повторы и застрявшая доставка;
- сохранение оплаченных пользователей и исключение paid/trial-комнат из cutover;
- начало первой волны реального окончания trial через три дня, успешные/неуспешные
  первые платежи и правильное изменение прав.

Production-наблюдение после трех дней нельзя заменить локальным Test Clock.
Диагностика не публикует токены, ключи, сырые provider responses или частные
данные пользователей. Материалы поддержки готовятся заранее; отправка сообщений
от имени владельца требует отдельной авторизации.

### 21.2. Как обновлять этот документ

Для каждого следующего блока записывать:

| Поле | Содержание |
| --- | --- |
| Требование | Номер раздела/строки матрицы, какое поведение нужно |
| Изменение | Что фактически поменялось и почему |
| Источник | Commit/PR, нужный контракт или согласованное решение |
| Проверка | Команда или пользовательский сценарий, среда, версия/артефакт |
| Результат | PASS/FAIL/не проверено и точная граница доказательства |
| Остаток | Конкретное действие, мешающее полной приемке |

Закрывать частичный пункт можно на уровне локальной реализации, не закрывая
весь staging/release-пункт. При обнаружении нового факта обновлять выводы
по реальному коду и продукту. Не следовать старой галочке вопреки изменившимся
условиям. Отмененные решения оставлять только как явно обозначенную историю.

Новая сводка становится общей точкой чтения; подробные source evidence и
операторский runbook остаются первичными техническими приложениями. Будущие
изменения статуса должны согласовываться с текущим состоянием и активным планом,
чтобы документы не начали описывать разные версии продукта.
