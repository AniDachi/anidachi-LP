## Behavior and boundaries

Free/Plus/Pro retain 4/6/15 total participants and four simultaneous cameras.
Their 4/6/8 media seats allow microphone use plus requesting a camera slot.
Actual admission order assigns free seats. The host has one seat control per
person, including themself; an existing listener is not automatically promoted
when a seat becomes free. A genuinely new entrant can receive a free seat.

Muting a microphone or disabling a camera keeps the seat. Revocation removes
the seat and both publication grants, cancels pending capture, and preserves
incoming media. It persists by verified user ID across socket replacement and
rejoin in the same room. Regrant requires the participant's own action before
capture can resume. Host authority itself does not require a seat. Current
disconnect grace, room ending, paid renewal and Free usage metering are unchanged.

The extension advertises protocol 3 and reads strict v2/v3 snapshots, ACKs and
errors. A durable lease pins the room's version; create retry and renewal never
convert an existing room. Older clients receive update-required before claiming
a session in a v3 room. V2 rooms retain the earlier independent device controls.

This change does not alter billing, history, invitation membership, supported
providers, extension host permissions or the fixed drawer width.

The real-browser scenario exposed redundant SDP offers during simultaneous
device changes. Revision tracking removes duplicate browser negotiation events;
the follow-up correction checks the negotiated answer before consuming a
duplicate remote request. Genuine new direction changes and failed/disconnected
transport still trigger negotiation. No signaling allowance, quality budget,
recovery role or test pacing was relaxed.

Revocation also exposed a synchronous ordering race: the old peer set received
voice-stop/late ICE after the server had already removed those media edges.
The actual overlay now applies the new permitted peers before stopping capture;
late callbacks cannot signal an excluded peer. Authorized receive and ordinary
local device-off behavior remain available.

Final whole-branch review found a persistence-error gap: successful rollback
sent generic `ERROR/MEDIA_UNAVAILABLE`, leaving the seat button pending and
turning off the host's camera through unrelated device-error handling. A v3
`MEDIA_SEAT_RESULT/MEDIA_UNAVAILABLE` now includes the original request/session
and restored snapshot only after durable rollback succeeds. Failed rollback
still closes the requester with 1011. Actual RoomClient and mounted-overlay
regressions verify retry, stale-result fences and unchanged own capture. The
final scoped re-review found no remaining actionable findings.

The earlier apparent v3 first-frame delay included participant waiting time:
the harness incorrectly treated an unknown snapshot version as v2 and started
clocks before any camera was requested. A live regression failed with nonempty
camera-clock IDs while every device was off. The correction waits for a known
protocol and starts v3 clocks at the remote camera grant. All final runs pass
this clock-boundary check and retain the strict 6000 ms p95 budget.

## Rollback

Retain additive SQL and readers that understand both room versions. Stop new v3
creation with a compatible Web correction that rejects new v3 create requests
before the create RPC, while preserving connect, renewal and active rooms.
Do not revert the entire Web/Worker/client stack to a version unable to read v3,
or reinterpret existing v3 rooms as v2. Use a compatible fix or the existing
room-ending lifecycle before removing v3 readers. Personal history and billing
data are outside this rollback scope.
