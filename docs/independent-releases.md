# Выпуск одной задачи

У каждой задачи своя ветка и свой выпуск. Общий тестовый сайт находится на staging.anidachi.app.

1. Получи последние изменения командой `git fetch origin`. Создай ветку от опубликованного кода командой `git switch -c codex/seo-task origin/main`.
2. Разрабатывай локально. Выполни `pnpm dev:check --base origin/main` и проверки затронутой части проекта. Запушь свою ветку и открой PR в `staging`.
3. После зелёного CI сам нажми **Create a merge commit** в PR в `staging`. Сохрани свою рабочую ветку. Автоматика проверит именно её последний коммит отдельно от других задач и запустит проверки на общем стенде. Для расширения она дождётся проверенного staging ZIP, для изменений Worker и БД — соответствующих тестовых деплоев.
4. После успеха в GitHub появится один PR из твоей ветки в `main`. Он может оставаться открытым сколько угодно. Для SEO проверь страницы на тестовом сайте. Для Prime установи тестовую сборку и проверь воспроизведение ведущего и гостя. Готовую задачу автор выпускает кнопкой **Merge** после обязательных проверок. Публичная публикация расширения выполняется отдельно.
5. Если добавил код, используй ту же ветку и новый PR в `staging`. Старый результат относится только к прежней версии. Если `main` успел измениться, влей в свою ветку свежий `origin/main` и повтори проверку. Никогда не обновляй рабочую ветку из общего `staging`.
6. После выпуска автоматика сверяет `main` со `staging` и синхронизирует их через PR. Конфликт останавливает синхронизацию до разрешения. Затем рабочую ветку можно удалить.

Если тест упал, открой **Actions → Accept a staged feature** и посмотри шаг с ошибкой. Для временной ошибки повтори неудачные jobs. Если изменения конфликтуют или на стенде отменили часть твоей задачи, согласуй итог и отправь исправленную версию на стейж. Ручная отметка в PR не заменяет результат проверок.

Для работы нужен доступ **Write** к репозиторию, доступ к тестовому сайту через менеджер паролей команды и обычный вход в GitHub под своим аккаунтом. Рабочей машине и ИИ не нужны административный токен, доступ к production или секреты GitHub Actions.

Пока в твоей копии `main` ещё лежит прежняя инструкция по выпускам, после `git fetch origin` прочитай `git show origin/staging:AGENTS.md` и `git show origin/staging:docs/independent-releases.md`. Так оба разработчика смогут начать работать до публикации самой настройки.

### Инструкция для ИИ

Работай только в ветке одной задачи от свежего `origin/main`. Следуй `AGENTS.md` и матрице проверок. Первый PR открывай в `staging`. Сохраняй рабочую ветку для отдельного выпуска. После новых коммитов повторяй стейж. Покажи автору ссылку на тестовый сайт или ZIP и его собственный релизный PR. Слияние в `main` и публикация в Store требуют отдельного поручения автора.
